# Мониторинг Мастерской

Отдельный публичный мониторинг: таймер существующей входной VM запускает
GitHub Actions, который выполняет проверки Globalping из шести российских
городов и сетей. OpsPulse следит, чтобы мониторинг не перестал выполняться.
Финляндия исключена из текущего набора.
Ни код приложения, ни данные клиентов, ни доступы к Yandex Cloud сюда не входят.
Документ описывает новую схему. Реальные запуски видны в GitHub Actions;
подробный журнал переключения хранится локально в RESULT.txt.

## Где смотреть

- [Последний результат и история инцидентов](https://github.com/KlochkovN/masterskaya-monitoring/issues)
- [Запуски и их результаты](https://github.com/KlochkovN/masterskaya-monitoring/actions)

Проверяем основной сайт, API через edge и прямой API Яндекса. Сайт и edge
используют одну VM — это разные пути доступа, а не два независимых сервера.
Ожидаемый отказ HTTP 401 у API подтверждает путь до функции авторизации;
это **не** проверка YDB, расписания, входа пользователя или сохранения данных.

| Кострома | Ростелеком | 12389 |

это не проверка всех абонентов или всех сетей России.

## Оповещения

При подтверждённой проблеме создаётся issue с упоминанием владельца. При
восстановлении приходит комментарий, issue закрывается. Успешные проверки
не создают отдельных оповещений. Два измерения при проблеме выполняются в
одном запуске с паузой 10 секунд. Расхождение или отсутствие данных означают
неизвестную доступность, а не доказанный отказ Мастерской.

Неизменная проблема не порождает повторных писем через каждый интервал.
При изменении статуса или восстановлении приходит новое сообщение; колебания
статуса между запусками могут вызвать несколько писем. Замена набора сетей
закрывает старое предупреждение с пояснением, а не с ложным сообщением
о восстановлении исключённого узла.

Email-оповещения о доступности приложения отправляет GitHub, а не почта Мастерской. Их доставка зависит
от настроек аккаунта владельца. Ручной запуск с `test_alert=true` создаёт явно
помеченное тестовое уведомление, не отключая приложение.
Отдельное письмо OpsPulse означает пропуск подтверждённого выполнения самого
мониторинга, а не доказанный отказ сайта или базы.

## Границы и обслуживание

- Расписание задаёт systemd на VM — раз в 10 минут; GitHub `schedule` не нужен.
  GitHub всё ещё может задержать задачу в очереди или не выполнить её.
- Если последнему результату больше 15 минут, доступность неизвестна. Issue
  не умеет автоматически менять цвет, когда GitHub остановился. В новой схеме
  отсутствие heartbeat отслеживает OpsPulse: период 10 минут плюс 5 минут
  допустимой задержки. Независимость его внутренней инфраструктуры от YC
  принята владельцем как допущение, а не подтверждена поддержкой.
- Проверки идут из дата-центров и сетей доступа, не из всех мобильных сетей России.
- Без токена Globalping даёт 250 проб/час на IP; IP GitHub может быть общим.
  Обычный режим: 6 сетей × 3 адреса × 6 запусков = 108 проб/час,
  максимум с повторными подтверждениями — 216.
  Ручные запуски добавляют расход. Ошибка лимита отображается как отсутствие
  данных, покупки кредитов и автоматического повышения лимита нет.
- При необходимости добавьте `GLOBALPING_TOKEN` только в GitHub Actions
  Secrets: отдельная учётная запись даёт 500 проб/час. Не в файлы и не в чат.
- Внутри GitHub Actions используется краткоживущий `GITHUB_TOKEN` этого
  репозитория: чтение файлов и работа с issues. Для запуска задач с VM нужен
  отдельный fine-grained PAT только с **Actions: read and write**, сроком
  90 дней. Рабочая копия хранится на VM в закрытом файле и не публикуется;
  продлить или заменить ключ нужно до 24 февраля 2027 года. Workflow не запускается из PR.
- Тела ответов, cookies и авторизация Мастерской не сохраняются и не отправляются.
- MAX, почта, платежи, база и настройки PROD не изменяются.
- Интеграция с административной консолью Мастерской пока не подключена.

## Проверка и остановка

Локальные тесты: `node --test` и
`python3 -B -m unittest discover -s . -p 'test_dispatch_runner.py'` (без сети). Проверяются ответы,
ошибки провайдера, создание инцидента, отсутствие дублей и восстановление.
Плановая остановка: отключить `workshop-monitor.timer` на VM, дождаться
завершения текущей проверки и поставить рабочую проверку OpsPulse на паузу.
Не отключать GitHub workflow при обычном переключении: он нужен для внешнего
`workflow_dispatch`. Историю issues и запусков удалять не нужно.

Источники: [Globalping](https://globalping.io/credits),
[расписание GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

Независимость обработчика сигналов, планировщика и отправки email OpsPulse от
Yandex Cloud **не подтверждена**. Владелец принимает её как рабочее допущение
для переключения, а не как проверенный факт или ответ поддержки. Российский
IP входного адреса сам по себе не подтверждает размещение всех компонентов.

Новый путь: systemd-таймер на уже существующей входной VM → GitHub
`workflow_dispatch` → прежние проверки Globalping → прежние issues от
`github-actions[bot]`. Изменять авторство инцидентов или выдавать постоянному
токену право редактировать issues не требуется. Шесть российских сетей,
подтверждение сбоя и отсутствие повторных писем сохраняются.
В интерфейсе GitHub такой API-запуск может называться «Manually triggered»:
фактический запуск по таймеру подтверждается журналом systemd на VM.

`dispatch_runner.py` использует только Python 3 standard library; Node на VM
не нужен. Каждый запуск получает UUID в `external_run_id` и уникальное имя
GitHub run. Таймер ждёт завершения **именно этого запуска**, проверяет успех
job `check` и шагов `Test monitoring logic` / `Check public endpoints`.
После dispatch метаданные GitHub могут появиться не сразу: до 30 секунд
допускается ожидание их заполнения, но идентификатор, имя, репозиторий,
ветка, событие и путь должны строго совпасть до отправки heartbeat.
Последний шаг публикует отчёт до успешного завершения. Успешный HTTP-ответ на
запрос запуска сам по себе не считается выполненной проверкой.

После проверки завершения отправляется пустой POST в OpsPulse.
Этот heartbeat значит «мониторинг выполнился и опубликовал отчёт», **а не
«Мастерская доступна»**: результат `down` или `unknown` обрабатывается прежними
GitHub-оповещениями, но исправно выполненная проверка подтверждает работу
монитора. При остановке VM, таймера, недоступности GitHub или зависшем запуске
heartbeat не придёт; OpsPulse должен отправить письмо о пропущенном сигнале.
Доставка тестового DOWN-письма и возврат тестовой проверки в UP подтверждены.

### Установка после согласования доступа

Подготовленные файлы:

- `dispatch_runner.py` → `/opt/workshop-monitor/dispatch_runner.py`, root-owned,
  0644. Не помещать туда секреты.
- `systemd/workshop-monitor.service` и `.timer` → `/etc/systemd/system/`.
- `/etc/workshop-monitor/credentials.env`: root-owned, 0600, каталог 0700.
  Только два значения: `MONITOR_GITHUB_TOKEN` и `OPSPULSE_PING_URL`.
  Не печатать содержимое, не передавать токены через аргументы команд и не
  добавлять файл в репозиторий.
- GitHub fine-grained PAT: только `KlochkovN/masterskaya-monitoring`,
  repository permission **Actions: read and write**, без Contents/Issues write.
  Он позволяет запускать/читать Actions; это шире одной конкретной кнопки,
  но не даёт доступ к Мастерской, Yandex Cloud и данным клиентов.
- OpsPulse: интервальная проверка, период 10 минут, grace 5 минут, email
  включён. Бесплатный START включает 5 проверок и email; повторные напоминания
  на нём не заявлены. Нужна UUID-ссылка `https://opspulse.ru/ping/<uuid>`,
  не ключ управления аккаунтом. Runner принимает только такой HTTPS-адрес
  без логина, пароля, порта, query или fragment и не следует перенаправлениям.
  Отправляется пустой POST без GitHub-токена; успех — только HTTP 200 и JSON
  с `"status":"ok"`. Ответы и секретные адреса не выводятся в журнал.
  Сервису не передаются GitHub PAT, отчёт или данные клиентов.

С учётом принятого владельцем допущения о независимости OpsPulse от YC
подготовить секреты, затем опубликовать workflow с
`external_run_id` и новым `run-name` через сайт GitHub. Подготовленный workflow
**не содержит старого `schedule`**, чтобы два таймера не удваивали расход проб.
Не отключать workflow целиком: тогда внешний dispatch тоже перестанет работать.
После публикации дождаться завершения уже запущенных старых проверок и
проверки от публикации (push), затем включить systemd-таймер в том же окне работ; если запуск
новой схемы откладывается, не публиковать удаление прежнего расписания заранее.

Проверка файлов перед включением:

```sh
python3 -m unittest discover -s . -p 'test_dispatch_runner.py'
node --test
systemd-analyze verify /etc/systemd/system/workshop-monitor.service /etc/systemd/system/workshop-monitor.timer
systemd-analyze calendar '*-*-* *:03/10:00 UTC'
```

Служба работает с DynamicUser, закрытым StateDirectory и flock. Таймер UTC
срабатывает на 03, 13, 23, 33, 43, 53 минутах. Один запуск ждёт GitHub до
6 минут; общий systemd timeout — 7 минут. GitHub job ограничен 5 минутами:
runner успевает принять результат задачи, занявшей 4–5 минут, в том же тике.
После таймаута следующий запуск
продолжает ждать ту же задачу, а не создаёт очередь дублей. Состояние переживает
перезапуск VM. Повторный ручной старт менее чем через 9 минут после начала
уже законченной попытки пропускается без новой проверки и без ложного heartbeat.
Поэтому при включении дождаться штатного тика таймера, а не запускать службу
вручную незадолго до него: cooldown может пропустить ближайший тик.

Если ответ dispatch потерялся, UUID позволяет найти уже принятую задачу. Если
задача так и не найдена, runner намеренно не посылает повторные POST вслепую.
Через 15 минут и только после успешного полного ответа API, подтверждающего
отсутствие задачи с этим UUID, попытка отмечается неудачной. Следующий тик
таймера может создать новую. Если API недоступен/возвращает неполный список или
задача реально стоит в очереди, дубль не создаётся; OpsPulse сообщает о
проблеме. Не удалять состояние при работающей службе.

### Приёмка и границы

1. Первый штатный запуск службы по таймеру: GitHub run с UUID, выполненные шаги, свежий отчёт,
   затем принятый heartbeat. Проверить историю именно этой проверки в OpsPulse,
   а не только HTTP 200: runner дополнительно требует JSON `{"status":"ok"}`.
2. Два последовательных запуска **по systemd-таймеру** должны завершиться с интервалом
   около 10 минут. Ручные пуски вместо них не считаются приёмкой.
3. Независимое письмо о пропущенном heartbeat проверить на отдельном тестовом
   check, без отключения сайта/монитора. Не отправлять письма о ложном сбое
   приложения. После возобновления heartbeat проверить восстановление.
4. Проверить, что старый GitHub `schedule` отсутствует, параллельные ручные
   измерения не оставлены, расчётный максимум 216 проб/час не превышается.

VM остаётся общей точкой отказа сайта и **запуска** проверок. OpsPulse должен
сделать этот отказ заметным снаружи, но сам не выполняет шесть сетевых проб.
GitHub runner/Globalping также остаются зависимостями. Heartbeat не исправляет
их отказ и не доказывает доступность приложения. Истечение PAT, почтовый спам,
отказ самого OpsPulse и неверные настройки check — отдельные ограничения.
Для PAT нужен ограниченный срок и заранее запланированное продление; истёкший
токен не должен молча считаться успешной проверкой.

Источники по OpsPulse: [документация](https://opspulse.ru/documentation),
[тарифы](https://opspulse.ru/), [оператор и условия](https://opspulse.ru/legal).
